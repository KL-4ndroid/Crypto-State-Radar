# 幣安資料採集頻率

2026-10-30 查驗：目前的「每小時掃描」指每小時啟動一輪，深入分析會分批續跑；並非所有幣安 API 都只在 07 分呼叫一次。本次只補文件與計量，沒有改動已啟用的採集頻率。

| 工作 | 台灣時間 | 何時向幣安請求 |
|---|---|---|
| full_scan | 每小時 07 分 | 全市場基本觀察與最多 25 個深入分析 |
| drain | 每小時 03、08、13…58 分 | 有待處理或到期 active lifecycle 時，最多深入分析 100 個；idle / waiting 不採集行情 |
| validate | 每小時 04、09、14…59 分 | 有到期且取得 lease 的 validation jobs 時抓歷史 5m K 線；沒有到期工作時零上游請求 |
| Dashboard 一般讀取 | 可見頁面約每 60 秒 | 只讀公開 Redis 投影，不向幣安請求 |
| 人工掃描／研究採集 | 人工呼叫時 | 額外採集；不算自動排程的一輪 |

## 已確認的實際輪次

2026-10-30 的 18、19、20 時三輪：

- 07 分：觀察 522 個標的，深入分析 25 個，575 次上游 request，留下 497 個待處理。
- 08、13、18、23 分：各完成 100 個深入分析、各約 302 次 request。
- 28 分：完成最後 97 個，約 293 次 request，pending 歸零。
- 全市場這一輪基本觀察＋深入分析合計約 2,076 次 request，分布約 21 分鐘；這是當時 522 個標的的實測，數量會隨市場、失敗與新 setup 改變。沒有宣稱是 API weight 或計費單位。
- 完成後的 drain tick 仍檢查待處理工作，但程式會在 collect_market 前直接返回；需要時會重播 Redis 發布，這不會向幣安抓行情。
- 驗證是獨立工作，1h、3h、6h、12h、24h、3d、7d 的 signal horizon 到期後仍需取得後續價格，因此其幣安請求不包含在上述 2,076 次中。每次最多 20 個 jobs、40 秒／60 request 的預算。

後續每批會重新取得該批標的當時行情與歷史特徵，不是重播 07 分的同一份深入分析資料。目前未發現另一個全市場自動觸發來源；GitHub cron 已移除。

## 設計取捨

每輪只允許 25 個深入分析名額，故續跑用來完成全市場覆蓋；若直接停掉續跑，其餘標的會停留在待評估。若要嚴格限制「整個系統每小時只有一次採集」，必須重新選擇執行位置／容量、active lifecycle 延遲與 validation 頻率，再做單獨的變更驗收。

本次不因此調整模型或關閉 validation。新增的持久執行收據與 [24 小時驗收](current-status.md) 將量測每種 operation 的實際上游 request、閒置與錯誤數；之前未保存的 validation request count 不回填或當作零。
## 後續改善狀態

已新增 opt-in 的 [依待辦喚醒方案](demand-driven-scheduler.md)，預設關閉。上述正式頻率與請求量基準仍適用；目前尚未切換 demand 或增量歷史採集。
